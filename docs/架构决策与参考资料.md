# 架构决策与参考资料

版本：1.0 · 日期：2026-11-19

本文记录本轮评审形成的设计取舍，配合[主架构](学习平台内核参考架构.md)使用。外部材料仅支持所列机制的理解，不构成已完成本项目验证的证据。下列主要官方页面已在本轮讨论中查阅；未来实现时，应再次核对需要采用的具体版本与 API。

## 1. 决策记录

| 编号 | 决定 | 理由与实施影响 |
| --- | --- | --- |
| D-01 | 保留原领域模型，采用无头模块化单体 | 材料、位置、实例、作品、提交与判定的区分具有复用价值；当前通过模块依赖和写入口实现边界，不拆微服务。 |
| D-02 | 首版沿用关系状态、追加历史和持久任务 | 保留可追溯性与原子确认；不为全部状态引入事件重放、投影游标和事件 Schema 演进。 |
| D-03 | 命令/查询逻辑分开，共用数据库 | 写入执行业务约束，读取返回经授权结果；不要求不同数据库或消息中间件。 |
| D-04 | 公共 API 与有限 SPI 分开 | 宿主作者知道怎样调用，能力作者知道怎样实现；默认工具也用公开接口，不依赖内部特权通道。 |
| D-05 | 平台授权强制执行，教学反馈采用具名策略 | 减少首版策略语言负担，同时保留资源、关系、用途、分组与追溯的统一约束。 |
| D-06 | 执行定义只覆盖当前变化 | 步骤、依赖、交付和新尝试先行；静态条件发布时展开，动态条件和恢复语义明确；不建设任意工作流语言。 |
| D-07 | 声明与代码作者入口共享受控语义 | 代码构建器提供类型支持，不让任意代码绕过事务、权限、版本与恢复。是否现在建设完整 SDK 由实际接入决定。 |
| D-08 | 作品支持原始内容与关联只读表示 | 支持脱离编辑器回看；明确权威内容、来源修订和生成方式，不能默认转发全部格式。 |
| D-09 | 支持两种交付方式 | 严格来源槽位采用经验证源片段；通用作品槽位可接收客户端独立成果，降低工具接入门槛。 |
| D-10 | 来源关系、交付冻结与最小披露分别描述 | `sourceRef` 和摘要不自动证明源片段对应；独立文件也可能带隐藏私有内容；验证级别由平台维护。 |
| D-11 | 用四个主要实体帮助入门，不限制物理模型数量 | 尝试、操作结果、任务、定义版本等仍需明确归属；不把复杂性藏进无约束 JSON。 |
| D-12 | 以真实迁移与异质样例检验接口 | 两步阅读和双轮交卷先行，自评/独立成果按变化方向验证；不把“三插件”或“300 行”当作质量证明。 |
| D-13 | 文档随实现完善 | 先有短仓库入口、真实契约和验收清单；现有领域参考保留。无需先写完三套大型文档才继续迁移。 |
| D-14 | 迁移保留单一写入权威与历史未知 | 不制造历史版本、揭晓或独立作答事实；切换可对账，回退保留已产生的新事实。 |

## 2. 明确没有选为当前默认的做法

| 做法 | 当前不采用的原因 | 重新评估条件 |
| --- | --- | --- |
| 全量 Event Sourcing | 增加事件演进、重建、迁入迁出和运维成本；当前已有关系事务能承担核心保证 | 具体子域确实需要事件流作为权威来源，且收益与迁移成本被验证。 |
| 所有视图都异步投影 | 不同读路径的一致性需要不同；当前权限与确认状态不应依赖滞后视图 | 某些查询经测量需要预计算，且定义陈旧结果与重建行为。 |
| 任意 Policy 插件直接返回全量敏感数据的过滤结果 | 角色标签不足以授权，拿到全量数据后过滤也无法形成可靠边界 | 仅在受约束、可信策略及平台最终裁决下扩展。 |
| 任意 before/after 提交 Hook 链 | 让学习事实含义依赖插件顺序，并放大事务与重试风险 | 有明确、窄化且不会改变核心不变量的生命周期扩展点。 |
| 所有第三方工具必须部署服务端私有解析器 | 抬高简单工具接入门槛 | 需要验证私有结构、来源范围或自动评价语义时，增加相应可信能力。 |
| 仅凭截图与 sourceRef 声称已验证原稿片段 | 不能证明提取关系，也不能证明附加文件未携带未选内容 | 平台实际执行了所承诺的验证。 |
| 把 LSP/MCP 直接作为内核领域模型 | 协议解耦启发不能代替活动、提交与判定语义 | 有明确外部接入方时，在外层增加适配器。 |

这些是当前阶段的架构取舍，不是对相关技术的一般否定。事件溯源本身并不要求授权滞后；本项目暂缓它的理由是当前成本与收益，而不是认为它无法实现强授权。

## 3. 主要一手参考与具体借鉴范围

### 3.1 H5P：作者字段与内容校验

- [Library Definition](https://h5p.org/library-definition)：身份、版本、依赖与核心兼容描述。
- [Semantics Definition](https://h5p.org/semantics)：字段描述服务于作者编辑器及内容校验。

本项目借鉴同一份字段契约为作者、校验器和能力描述提供一致信息。H5P 文档中的同 major/minor 自动采用已安装最新 patch 行为，不直接用于本项目历史实例；本项目需要保留实际解析依赖与明确的兼容策略。

### 3.2 Open edX XBlock：作用域与组件边界

- [Fields API](https://docs.openedx.org/projects/xblock/en/latest/fields.html)：定义、使用位置和用户作用域的区分。
- [Runtime API](https://docs.openedx.org/projects/xblock/en/latest/runtime.html)：宿主服务边界的阅读入口。
- [Role of XBlocks 架构记录](https://github.com/openedx/openedx-platform/blob/master/docs/decisions/0006-role-of-xblock.rst)：记录早期广泛动态组件权限对性能与稳定性的影响，以及职责收缩的思路。

该架构记录查阅时状态标为 Proposed。其背景记载的经验与提出的后续决策应分别理解，不能把全部提案当作已完成现状。本项目借鉴身份作用域和限制跨模块访问，不采用整套 LMS。

### 3.3 VS Code：贡献点与开发者入口

- [Extension Manifest](https://code.visualstudio.com/api/references/extension-manifest)：兼容版本、贡献声明、运行入口和依赖。
- [Extension Anatomy](https://code.visualstudio.com/api/get-started/extension-anatomy)：静态贡献、激活与运行时 API 的区分。

本项目借鉴有限贡献类别、公开服务和最小样例。登记中心不是沙箱，也不是扩展可以获得任意内部对象的服务定位器。

### 3.4 Gutenberg：结构化组合

- [Metadata in block.json](https://developer.wordpress.org/block-editor/reference-guides/block-api/block-metadata/)：父子、祖先和允许子块的结构声明。

本项目在复杂编辑器确有需求时参考其组合约束。组件结构校验属于作者工具与宿主能力，教学依赖和证据槽位保持独立语义。

### 3.5 关系事务、CQRS 与任务可靠性

- [Microsoft CQRS pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs)：允许同一数据库承载分开的读写逻辑，消息系统不是必需条件。
- [Microsoft Event Sourcing pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing)：说明收益、事件演进、重建与迁移成本，并允许选择性采用。
- [Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html)：业务记录与待发送工作同事务保存；消费者仍需处理重复交付。
- [SQLite Write-Ahead Logging](https://www.sqlite.org/wal.html)：并发与运行特征的官方说明。

本项目采用同库命令事务和持久任务，按实测调整索引、事务长度与查询。是否更换数据库取决于实际写入竞争、容量和运维需求，不由“通用平台”名称决定。

### 3.6 Stripe：幂等契约的对照

- [Idempotent requests](https://docs.stripe.com/api/idempotent_requests)。

可借鉴操作标识和明确的重试语义，不能据此推断其整个内部架构。本项目稳定的是已确认业务结果身份；反馈字段仍按当前权限生成。Stripe 文档中不同 API 版本的响应重试与键保留方式，不应未经分析直接照搬。

### 3.7 Medusa 与 Vite：局部机制参考

- [Medusa Module Isolation](https://docs.medusajs.com/learn/fundamentals/modules/isolation)。
- [Medusa Compensation Function](https://docs.medusajs.com/learn/fundamentals/workflows/compensation-function)。
- [Vite Plugin API](https://vite.dev/guide/api-plugin)。

参考模块隔离、装配和生命周期；不引入整套框架。补偿工作流不代替本项目提交确认的同库事务，评估失败不能删除已确认交付。构建工具的通用 hooks 不能直接决定学习事实的权威处理规则。

### 3.8 XState：可选状态机实现

- [Persistence](https://stately.ai/docs/xstate/v5/persistence)。

可参考状态保存与恢复。官方文档提示恢复会重新启动 invocations，机器逻辑变化可能与旧状态不兼容。采用状态机库仍需自行实现事务、任务幂等、版本支持与副作用边界，不将库名称写成迁移的硬要求。

### 3.9 Jupyter 与文件交付

- [Notebook file format](https://nbformat.readthedocs.io/en/latest/format_description.html)：MIME bundle 的多表示结构。
- [Security in notebook documents](https://jupyter-server.readthedocs.io/en/stable/operators/security.html#security-in-notebook-documents)：不可信主动内容的处理。
- [OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)：上传类型、大小、内容与访问处理。

本项目借鉴多表示，另加作品版本、权威内容、来源验证和片段权限。服务端不解析每种私有工具格式，并不代表无需通用上传验证或可以直接执行导出的脚本。

### 3.10 渐进迁移

- [Martin Fowler：Strangler Fig](https://martinfowler.com/bliki/StranglerFigApplication.html)。

参考按边界逐步替换的方式。具体执行以本项目的实例写入归属、旧新映射、对账和回退为准，不以架构名词替代迁移证据。

## 4. 原文内容处理说明

原文的学习对象、目标、编排、渲染工具、作品与提交、活动运行、学习数据、调度、扩展、版本、分享和 Agent 主题均在新版保留。新版主架构第 17 章提供定位映射。

本次主要改动：

1. 将全平台愿景、核心职责与当前实施范围分开，明确谁拥有写入口。
2. 加入 18 项可被验收引用的不变量，区分原则已经确定与实现尚待核验。
3. 补充不同操作竞争、持久任务乱序、当前权限投影、旧版本运行和迁移事实的约束。
4. 将教学策略收敛为可信具名实现，保留统一授权与聚合范围限制。
5. 加入独立冻结交付物路径，避免要求所有工具先实现服务端私有格式解析。
6. 将原文较长的作者 YAML 改为明确语义、接入示意和场景验收，不把作者预演样例误当作已存在的可执行 DSL。
7. 项目引用按两仓实际边界整理。内核使用本仓的公开契约和练法声明，OwnClass 的产品契约、DSL 与旧接口按对应工作包核对。

已对照原内核修订 `d70a5ff`。两步阅读三题、八分钟硬截止、整篇初判和连续改判，以及 OwnClass 预备实例的条件换版、固定包消费与跨库恢复边界，保存在[本仓验收与兼容约定](学习平台内核参考架构.md#18-本仓验收与兼容约定)。旧参考索引保留在下表。

## 5. 今后怎样修改架构

修改核心契约时，至少写清：遇到的真实场景、现有接口为什么不足、受影响的不变量、旧实例和旧交付如何解释、迁移与回退方式、可重复验收。单个工具的便利性不足以证明应扩大核心职责。

外部框架升级不自动要求修改本项目公共契约。先核对实际依赖与已有行为，在相应切片验证后再更新工程说明与版本支持范围。
